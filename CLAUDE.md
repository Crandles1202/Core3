## Build

```bash
~/bin/build            # ninja-debug incremental build (runs IDL), Debug, ccache
~/bin/build clean      # clean rebuild
```
- `~/bin/build` forces `-DENABLE_BUILD_CLIENT=OFF`, so `bin/core3client` (bot client) is **not** built by it.
  To build the client: `CMAKE_ARGS=-DENABLE_BUILD_CLIENT=ON ~/bin/build` (caller's `CMAKE_ARGS` are appended
  after the OFF, and cmake keeps the last `-D`). The next plain `~/bin/build` switches it back OFF, but an
  already-built `bin/core3client` stays.
- Incremental rebuild with a warm ccache is ~3.5 min wall clock; a changed `.idl` regenerates code; a small edit to a rarely included one (the `WeatherManager` getter) rebuilt in 16 s, a widely included one costs much more.
- **Custom strings / client data** live in `tre-src/` and are packed into `finalboss.tre` (`swg tre build`).
  `swg start` and `swg test unit` build + install it into `/tre` themselves; the server caches string
  tables in its ODB, so `swg start` adds the `reloadstrings` argument whenever the archive changed.
  The client needs the same file in its folder plus a `searchTree_00_N=finalboss.tre` line in
  `swgemu_live.cfg`: `swg tre install --client '<client folder>'` does both (folder remembered in
  `~/.swg-lab/client-dir`, so a plain `swg tre install` keeps the client current too; `swg tre patchcfg FILE`
  is the cfg step alone, `swg tre status` reports the client file + cfg state). The first archive in `Core3.TreFiles` wins, so ours is listed first in
  `config.lua` (and `Core3.TreManager.LatestTre` must name it or `ConfigManagerTest.TreFiles` fails).
- Lua-only changes need no rebuild. `swg cmd reloadscreenplays` re-runs `screenplays.lua` into each thread's
  *existing* Lua state on next use (globals persist, functions are redefined, screenplay `start()` is **not**
  re-run, so nothing re-spawns). Mobile/conversation/manager Lua lives in other Lua states and needs a restart.

## Run / stop

- **Never Ctrl+C / kill the server.** Stop it by typing `shutdown` at its console and waiting for clean exit.
- `~/bin/run` (Chuck's interactive way): rotates `screenlog.0`, resets the `admin` account password from
  `$ADMIN_PASS`, starts `gdb core3` inside `screen -S swgemu-server`, and attaches.
- `tools/swg` (Claude's way, tmux session `swg`) — see Test commands. Do not run both at once
  (`pgrep core3` first).
- Boot takes ~45 s; ready when the console prints `[Core] initialized` followed by `READY`.
- **Three servers** (2026-10-26): the **bench** (`~/workspace/Core3`, ports 44xxx, database `swgemu`) and **bench2**
  (`~/swg-bench2/Core3`, ports 46xxx, `swgemu_bench2`) each run gates, deploys and builds, so two agents test at the
  same time without waiting — by convention claude on the bench, alice on bench2 (`export SWG_INSTANCE=bench2` in her
  session); the **live instance** (`~/swg-live`, ports 45xxx, `swgemu_live`) is for Chuck's play and the citizens and
  **is production** (2026-10-26, Chuck's call): it runs the newest `chuck-stable-*` tag and nothing else, restarts only on `swg live deploy` (snapshot first) or by hand, never runs a test, a scenario or a bot, has no lab characters, and the citizens live on it as players. New content is played on the bench (`swg live client --bench`) before it is tagged. All binaries are named `core3`: the
  tooling tells them apart by working directory. Merges into `unstable` happen on the main bench only. One game client
  folder serves all three through `swg live client` / `swg live client --bench` (one line in `swgemu_login.cfg`).
- Console commands (`help` lists them): `shutdown`, `save`, `info`, `chars`, `reloadscreenplays`,
  `reloadmanager`, `loglevel`, `broadcast`, `runLuaFunction module:function[:arg...]`, `dumpcfg`.
- Chuck's client connects to `127.0.0.1` over UDP, which needs WSL **mirrored** networking
  (`C:\Users\rac35\.wslconfig`: `networkingMode=mirrored`; re-enabled 2026-10-18, nat copy kept as
  `.wslconfig.nat.bak`). Under nat the client hangs at "Connecting to the Login Server" while the lab bot,
  inside WSL, still works. Changing it needs `wsl --shutdown` from Windows: stop the server first.
- Known baseline log noise (filtered by `swg logs --errors`): `[TemplateManager] ERROR - unknown appearance
  type SPRT` (upstream: the server's appearance loader has no sprite reader; fires when a character with
  randomized missions in their bag logs in), and `[MantisDatabase0] ERROR - 1045: Access denied for user 'swgemu'` (and the
  matching `[Console]` line). Not ours; ignore when diffing ERROR lines. In `bin/log/core3.log` only: `handleNetStatusRequest
  … StreamIndexOutOfBoundsException at 8` every 5 s per connected bot client — engine3's own `NetStatusRequestMessage` is
  4 bytes (opcode + tick) while engine3's server handler reads the real client's longer form; the tick is parsed before
  the throw, so nothing is lost. Both sides are in the submodule; not fixable from Core3.

## Working in parallel (several agents)

See [docs/BOARD.md](docs/BOARD.md): the lanes table (who is on what) and the rules. In short: the main checkout
`~/workspace/Core3` is **the bench** (the one server runs from it; nobody edits files there); every agent works
in its own worktree (`swg agent new <name>` → `~/workspace/Core3-<name>` on `feature/<name>`, identity in
`.swg-agent`); `swg bench use <branch>` locks the bench and deploys a commit (reload / restart / build chosen from
what changed); every server-touching `swg` command runs under that lock and refuses other agents (`SWG_WAIT=1`
queues); `swg test all` records a gate pass per commit and `swg bench merge <branch>` merges `--no-ff` + pushes
only with one; `swg bench release` hands the bench back. `swg status` shows the lock; `swg cmd --shared` is for
read-only oracles (the planner uses it). A worktree has its own memory directory for Claude, so anything another
agent must know goes in the repo docs, not in memory.

## Branch and release rules

- `unstable` is the main branch (tracks `origin/unstable`). Upstream: `swgemu/unstable`.
- New work goes on `feature/<name>` branched from `unstable`, then merged into `unstable` with `--no-ff`.
  Doc-only touch-ups (status, to-do ticks) may go straight onto `unstable`.
- Stable points are tagged `chuck-stable-YYYYMMDD` (`swg live tag`; the older `stable-20260523` tag predates this convention) and
  are the only thing the production server runs (`swg live deploy`). First one: `chuck-stable-20261026` = `10f6472af2`.
- Remotes: `origin` (crandles1202/Core3, the only push target), `swgemu` (upstream), `mtg` (ModTheGalaxy),
  `flurry`, `orkwerks` — all non-origin remotes are fetch-only.
- **Ask Chuck before:** loading a snapshot, or touching his own accounts (`Chuckertons`, `chuck`). Since
  2026-10-20 Chuck's standing permission covers merging into `unstable` through the gate, pushing, and creating
  citizen accounts (`tools/citizens/citizen new`) — but the auto-mode classifier still refuses a merge into
  `unstable` from Claude, so Chuck runs `tools/swg bench merge <branch>` (or `! git merge …`) when a gated branch
  is ready.
- **Never commit passwords or secrets.** `config-local.lua` (`DBSecret`), `~/.env`, `~/.my.cnf` stay out of git.
- Commit messages: Chuck uses `Phase X.Y: <what>`; keep that style for roadmap work.

## Gotchas (read before writing Lua or tests) — detail in [docs/dev-notes.md](docs/dev-notes.md)

- `SceneObject(p)` / `CreatureObject(p)` / … return one **shared wrapper per class**, re-pointed on every
  call. Never keep `local o = SceneObject(p)` across another `SceneObject(...)` call; wrap inline.
  Breaking this throws a C++ exception that `pcall` can't catch and dirties the console Lua stack.
- There are many Lua states. Screenplay Lua can't see manager globals (`shuttleportAwayTime`,
  `commonStartingItems`), mobile/conversation templates, or `FBFeatures`. Sandbox-`loadfile` the file
  to inspect it (pattern in `fb_lab_tests.lua`).
- `reloadscreenplays` re-runs `screenplays.lua` into the existing state: functions update, `start()` does
  not re-run, nothing re-spawns. Mobile/conversation/manager Lua needs a restart.
- Non-combat mobiles still need `mobType`, `chanceHit`, `damageMin/Max`, `baseHAM/HAMmax` > 0 or the
  unit tests fail.
- Non-admin accounts create one character per hour; failed attempts reset the timer. The name filter
  runs first, so a declined name does not count.
- Allow-list rules match the whole command: run `git merge`, `git push`, `tools/swg …` as a single
  command per Bash call, never inside `a && b`. The classifier still refuses some things (remote
  URL changes, remote branch deletes, `git checkout -- <conf file>`); hand those to Chuck.
- The admin `/weather <n>` command stops the automatic weather pattern on that planet until `/weather enable`;
  use the lab's `weatherSet` (Lua `setZoneWeather`) to force weather without stopping it.
- An AI agent leashes back to its spawn point when sent or teleported far away; move its home too
  (`AiAgent:setHomeLocation(x, z, y, nil)`) before long walks. Short legs (patrols, convoy) are fine.
- **Placing a building** (2.11/2.12b): prefer the in-game site builder; by hand the pattern is `spawnSceneObject(zone, "object/building/…iff", x, z, y, 0, cos(h/2), 0, sin(h/2), 0)`
  creates the structure *and* its cells (not persisted: spawn at every boot, find cells by name with
  `BuildingObject:getCellName(i)`, never store cell ids). Room coordinates: cell-local x = floor-mesh x,
  cell-local y = floor-mesh z, cell-local z = the floor height (`appearance/collision/<pob>_r<N>_<room>_collision_floor.flr`,
  VERT chunk, little-endian floats). Footprint = the `r0` exterior floor's extents — check the lot against
  every stock footprint from `snapshot/<planet>.ws` (WSNP/NODS/NODE DATA, payload little-endian) before
  choosing it — `tools/lotsurvey lots <planet> <x> <y> --template <building iff>` does exactly that and
  `lotsurvey rooms <iff>` prints the rooms; the lab's `spawnBuildingAt`/`buildingInfo` oracles spawn and measure a candidate.
  **Furniture is client-only** (the building's `interiorlayout/*.ilf`; the server never loads it), so neither
  the placement audit nor line of sight can see an NPC standing in a table: `tools/lotsurvey check <iff> --lua
  <screenplay>` (or `--spot room,x,y`) tests spots against the furniture boxes — run it for every indoor spot
  and keep it in the scenario (trade-hall does). Stock city files are not a safe source of spots either (their
  Trade Hall "mercenary" point is inside the bar counter).
- Starting a conversation needs same cell, ≤ 5 m and line of sight to the NPC, and fails silently otherwise. The bot's `converse` therefore asks twice (10 s each) before failing (7.5; four gate flakes on the old single 5 s wait).
  **Before trusting an NPC spot:** `swg cmd "runLuaFunction FbLabTests:placement:<name>"` (line of sight to
  probes 3 m around, height above terrain, drift; `checkPlacement` runs it for every FB spawn in `swg test lua`),
  then `gotoNpc:<char>:<name>` and look at it in the client — the server's collision data misses some decorative
  world meshes, so an 8/8 spot can still be hidden behind a plinth (HN-7 at the starport, 2026-10-18). A wrong
  `cellID` makes `spawnMobile` fall back to the cell-local numbers as world coordinates (Rori droid at 29,0,
  84 m underground); the audit's terrain rule catches that. Stock commoner templates wander unless
  `AiAgent:addObjectFlag(AI_STATIC)` (+ `clearOptionBit(AIENABLED)` when not pvp-flagged).
- Spawns made by server events (seat churn, respawns) are recorded in *that* Lua state's `FbLabTests.spawns`,
  invisible to the console; the shared registry in quest status (`FbLabTests.registryAdd/registryLive`, written
  by the `spawnMobile` wrapper in every state) is the truth across states — `liveSpawns`, `checkNpc` and the
  Lab Remote read it. Keep per-window state in quest status too: SUI callbacks run on whichever thread
  handles the packet (pattern in `fb_lab_remote.lua`).
- Screenplay table fields set in `start()` are not visible from the console or server-event Lua states;
  persist cross-call state with `setQuestStatus`/`getQuestStatus` (keys without `:`). `getTerrainHeight`
  needs a creature; use `getTerrainHeightAt(zone, x, y)` when there is none.
- `SceneObject:getDirectionAngle()` returns **degrees** (`Quaternion::getDegrees`), not radians: never wrap it in
  `math.deg` (that bug sat in the Lab Remote's *Where am I* heading, the site builder and three lab oracles until
  2.12g). Heading convention everywhere (snapshot, `spawnSceneObject`, sites): yaw about y, `qw = cos(h/2)`,
  `qy = sin(h/2)`, read back as `2·atan2(qy, qw)`.
- IFF `FORM` sizes count the 4-byte type tag that follows the size (chunk sizes do not) — the first version of the
  snapshot writer was 4 bytes short on every form. `tools/worldedit check` is the guard: byte-identical roundtrip
  of all ten planet snapshots.
- **Village encounter base** (`quest_tasks/encounter.lua`, used by the 4a.1 visits): define
  `isEncounterFinished(pPlayer)` (a missing one reads as *finished* and nothing spawns), check the return of
  `start()`, and clear `AI_FOLLOW`/`AI_ESCORT` + `setFollowObject(nil)` before despawning a follower (the
  helper's deferred despawn re-schedules forever while the follow stands). Its despawn events are keyed to the
  *player*, so stamp every visit with a generation (`FbAttunement.visitTaskStart` / `visitHandleDespawn`) or
  an earlier visit's timer removes the next visitor. A visitor that must survive the player's logout stops
  following, goes `AI_STATIC` and is re-homed on the terrain where it stands (`FbTrials.standStill`). Encounter
  spawns are invisible to `findNpc` unless the screenplay adds them to the lab registry itself.
- **Bot client packet dispatcher** (`ZonePacketHandler::handleMessage`) switches on the packet's *opcount* first: a new
  `case` goes into the branch for its opcount (UpdateTransform = 8, CmdStartScene = 9) or it never runs, silently.
- **Bot client packets to the server** (ObjController): after the header's oid, `DataTransform` 0x71/0xF1 carry the
  payload at once, but `EmptyHopper` 0xED (and others whose callback says "skip passed player") expect an int pad and
  the player oid again first — read the callback's `parse()` before writing a new packet. The **AI navmesh leaves out a
  port's pad** (and structure footprints): `findPath` ends at the mesh edge, so `tools/seat` finishes a walk to a
  terminal or shuttle with a straight final leg (players are speed-checked, not collision-checked). `BuildingObject::
  getCell(n)` is keyed by cell *number* (1..N) and `getCellName` wants that number, not the cell's oid.
- **Scenarios and the weather:** a natural Tatooine sandstorm sends Tusken raiders to the outskirts (3.9) where
  scenarios park characters; `swg test all` and `lib.sh` clear the sky first. A CommandQueueRemove with `error=1
  state=N` names the *locomotion* that refused the command (20 = dead, 19 = incapacitated, 14 = sitting). A scenario's
  `trap - EXIT` before `finish` skips its cleanup on success: call `cleanup` explicitly.
- **Which `tools/swg` you run is who you are:** the lock identity comes from the `.swg-agent` next to the copy you
  invoke. `~/workspace/Core3/tools/swg bench use …` from a worktree takes the lock as "bench", and the worktree's own
  tools (`tools/seat`, `citizen`, the pilot's lab calls) are then refused as "alice" — silently, for anything that reads
  lab lines. Always run the worktree's `tools/swg` (CLAUDE.md's `tools/swg …` means that one). **And which server you talk to is `SWG_INSTANCE`:** seat and pilot state is shared by the bench and the live instance, so `crew`/`seat` record the instance per seat and refuse to touch a seat of the other one (a bench-side `crew down` logged two live citizens out on 2026-10-26); every command for a live citizen needs `SWG_INSTANCE=live`. The instance names and login ports are one table in `tools/seat`, `crew`, `citizen` and `scenarios/lib.sh` (`bench` 44453, `live` 45453, `bench2` 46453; `SWG_LOGIN_PORT` wins, an unknown name is refused), so a seat scenario on the second bench runs under `SWG_INSTANCE=bench2` with no port flag.
- **Wild creatures spawn only around a player who moves** (`SpawnArea::notifyPositionUpdate` → `tryToSpawn`, lairs near the
  player, never inside a city's no-spawn circle): an oracle count at a quiet spot says nothing about the hunting there — walk
  a bot through it first. A **zone switch counts as a move**: the visions scenario came home from the vision plane into a
  fresh scyk lair on its own spot and the trigger refused a fighting character (two gates 2026-10-26); lab
  `clearWild:<planet>:<x>:<y>[:radius]` removes wild lairs and creatures (never players, pets or lab spawns) around a
  scenario spot — call it before a check that needs the character out of combat. The **bench kills idle citizens**: every gate's `sandstorm` scenario sends Tusken raiders over Mos
  Eisley's east outskirts (Teyla died there 2026-10-22); a dead character gets the revive window on login and the pilot's
  `clone` tool answers it. The `story-ticker` scenario fires the weekly story in every gate too: five level-19 Tusken
  raiders camp at 3985,−4770 for a week after each bench run (`FbLabTests:story` says where) — a hunting ground is
  chosen with lab `threats:<char>:300` in hand, never by creature names alone. A player's stored level is only recomputed
  when a skill box is awarded (`calculatePlayerLevel`): a veteran start made unarmed read level 1 for ever, so since 7.5 the login hook recomputes it from the weapon in hand (`FBLogin.recomputeLevel` → `CreatureObject:recomputeLevel()`; lab `level:<char>`, scenario `level-login`); between logins a weapon change still leaves it stale, and the lab's
  *fighting strength* (best weapon line's `private_<weapon>_combat_difficulty`) is the number to compare with.
- **`AiAgent:getCreatureTemplateName()` on a snapshot NPC** (a stock static agent, oid below 2^24) had no creature template
  and dereferenced null — the server halts in gdb, the oracle prints nothing, and every later `swg cmd` answers nothing:
  read `swg status` (HALTED IN GDB) before blaming the Lua. Guarded since 7.5 (returns ""). **An indoor path ends at z 0**
  unless `pathTo` lifts it (it does since 7.5): `findPath` returns the target at the z it was asked for, the walk puts the
  character under the floor, the server accepts it, and an NPC conversation is refused silently (`checkLineOfSightInBuilding`
  rays from the character's z + 1 through the floor). `seat.action(…, timeout=)` is the socket's wait, not the action's. One sample start in 51 opens the server's *concentrated sample* window (`@survey:cnode_t`/`gnode_t`) instead of sampling, and row 0 reschedules the sample 25 s out: an unanswered server window reads as a silent timeout, so `tools/seat sample` (`sample_seat`) answers it and retries (gate flake 2026-10-23).
- **The terrain refuses ±8192** (`TerrainManager::getHeight` out of bounds) with a warning *and a stack trace per call*: a
  scan that touches the planet edge floods the console thread for minutes while `swg status` still says RUNNING. Keep every
  terrain lookup strictly inside the planet; the resource oracle's best spots are land-only (`getWaterHeightAt`).
- **Wounds, not regeneration** (2026-10-28): a pool regenerates only up to max minus wounds (`healDamage`), and nothing a
  citizen does clears a wound except the FB-21 medical droid (free, in every medcenter); Teyla sat two days at 585/1100 asking
  for a medic. The ham line prints `wounds=h/a/m shock=N` (Lua `getWounds`/`getShockWounds`), the pilot's condition says
  *wounded*, its `clinic` tool walks to the droid (lab `clinic:<planet>:<x>:<y>`). **A travel point's shuttle is the nearest
  one**: `travelPoints` used to keep the last shuttle within 120 m, so Mos Espa Starport resolved to the East shuttleport's
  shuttle 66 m away and `boardShuttle` (which matches the ticket against the point nearest the character) refused nine valid
  tickets; `checkShuttles` asserts one shuttle per travel point.
- gtest's `<<` cannot print an engine3 `String`; use `.toCharArray()` in assertion messages.
- **Threads in engine3 code must be engine3 `Thread`s** (subclass, `run()`, `start()`, `join()`), never `std::thread`:
  `Locker` skips the lock when the lock's holder equals `Thread::getCurrentThread()`, and on a foreign thread both are
  null for a free lock — so every `Locker` is a no-op there, a condition wait re-acquires the mutex on return and nobody
  releases it (the seat's first driver threads left the zone mutex owned by a dead thread; the client then deadlocked
  at shutdown). A hung client is read with `sudo gdb -p <pid>` (plain gdb: `ptrace: Operation not permitted`);
  `p ((pthread_mutex_t*)ADDR)->__data.__owner` names the LWP that holds a mutex.
- Lua bindings read arguments from the top of the stack and do not validate: a call with the wrong
  arity (`faceObject(pNpc)` instead of `faceObject(pNpc, true)`) passes garbage/null into C++ and
  segfaults the server (or, for the global functions, silently reads garbage: `writeScreenPlayData(pPlayer, screenplay, key, value)` / `readScreenPlayData(pPlayer, screenplay, key)` take the screenplay name and the key as *separate* strings — folding them into one left 4a.1's score at zero without any error). Check the binding's signature in `Lua*.cpp` before using a method for the first
  time. If the server is halted at a gdb catchpoint (`swg status` says HALTED IN GDB), a null-deref in a
  leaf function can be skipped with `frame N` / `return` / `continue` in the tmux pane; otherwise
  `swg stop` kills it from gdb and keeps the backtrace in `~/.swg-lab/crashes/`.
- `git ls-files -v | grep ^S` shows skip-worktree files. `resource_manager_spawns.lua` is written by the
  server and must stay that way; nothing else should carry the flag.
